Arquitectura del Agente

Victoria es un sistema multi-agente construido con Google ADK (Agent Development Kit) usando Gemini 3.1 Flash Lite. El usuario interactúa por WhatsApp con una sola personalidad (Victoria), pero internamente el router distribuye a sub-agentes especializados.

Cómo Trabaja Victoria - Flujo Detallado

Caso: Resuelve Autónomamente (consulting)

Usuario consulta estado de un estudio de arrendamiento.

  1. Usuario: "Quiero saber el estado de mi estudio"
  2. Router → victoria_consulting
  3. Victoria pide radicado → usuario lo da
  4. Victoria llama herramienta consult_study_state
  5. Victoria responde con el estado (ej: "Tu estudio está aprobado pendiente de biometría")
  6. Fin: Resuelto sin humano

Caso: Escala a Humano (increment)

Usuario solicita un cambio contractual (incremento de canon, cambio de rol).

  1. Usuario: "Necesito hacer un incremento"
  2. Router → victoria_increment
  3. Victoria recopila datos (7-10 turnos): radicado, documento, tipo cambio, email, teléfono...
  4. Victoria muestra resumen de datos al usuario
  5. Usuario confirma: "Sí"
  6. Victoria emite JSON: {"agent_action":"approve_increment", ...datos...}
  7. Plataforma intercepta → Transfiere a agente humano para aprobación

Caso: Escala a Humano (schedule)

Usuario quiere agendar una cita o necesita verificación presencial.

  1. Usuario: "Quiero agendar una cita para firmar"
  2. Router → victoria_schedule
  3. Victoria valida el estudio con validate_study_for_schedule
  4. Victoria NO tiene integración con sistema de citas
  5. Victoria emite: {"agent_action":"transfer_to_human"}
  6. Transfiere a humano porque no puede agendar directamente

Hallazgos Clave

  1. Victoria hace el trabajo operativo pero no cierra. En incrementos y traslados, la IA recopila exitosamente todos los datos (7-10 interacciones) pero la aprobación final siempre requiere humano. La IA funciona como "recepcionista inteligente" más que como "resolutora".
  2. victoria_schedule escala por limitación técnica, no de negocio. El agente de agendamiento no tiene herramientas para confirmar citas directamente. Esto es un gap de integración, no una política de negocio.
  3. La tasa de escalación creció de Jun (76%) a Jul (83%) con la adición de victoria_schedule. En junio no existía el agente de agendamiento; en julio se agregó pero sin integración completa, generando más escalaciones.
  4. Solo 2 agentes resuelven sin humano: victoria_consulting (consulta estado) y victoria_advisor (orientación general). Juntos representan solo ~21% de la actividad.
  5. close_session aparece como patrón defensivo cuando usuarios envían el mismo mensaje 5+ veces, sugiriendo frustración o problemas de UX.

Recomendaciones

Impacto alto — Reducción estimada: 20% de escalaciones

Integrar sistema de agendamiento en victoria_schedule

Conectar victoria_schedule directamente con el sistema de citas para que pueda confirmar agendamientos sin transferir a humano. Actualmente el 100% de sus sesiones escalan por falta de integración.

Impacto alto — Reducción estimada: 15-20% de escalaciones

Auto-aprobación de incrementos estándar

Evaluar si incrementos estándar (por IPC, sin cambio de condiciones especiales) pueden aprobarse automáticamente una vez que Victoria recopila los datos. Incrementos no estándar seguirían requiriendo humano.

Impacto medio — Reducción estimada: 10% de escalaciones

Validación automática de traslados simples

Para traslados donde el estudio ya está aprobado y todos los datos son válidos, evaluar un flujo de aprobación automática con verificaciones programáticas (validar radicado, estado del estudio, datos del nuevo inmueble).

Impacto bajo — Mejora de UX

Reducir close_session por frustración

Investigar por qué usuarios envían mensajes repetidos. Puede indicar que Victoria no entiende la solicitud o que el flujo es confuso. Mejorar los mensajes de orientación antes de cerrar la sesión.
